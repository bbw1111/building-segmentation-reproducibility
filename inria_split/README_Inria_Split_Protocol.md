# Inria tile-level split and patch preparation

## Purpose

This folder documents the deterministic Inria data preparation and tile-level train/validation split used for the supplementary experiment.

## Files

- `split_protocol.txt`: concise description of the split and patch-generation protocol.
- `tile_split_master.txt`: explicit train/validation tile lists and expected patch counts.
- `tile_patch_mapping_generator.py`: preparation script. It reads the Inria `AerialImageDataset/train/{images,gt}` files, generates 512×512 patches at stride 1536, and writes a tile-level split record. Patch filenames retain the source tile name and coordinates.

## Protocol summary

- Source tiles: 180
- Validation selection: sort tile names lexicographically and assign every sixth tile (indices where `i % 6 == 5`) to validation.
- Train/validation source tiles: 150 / 30
- Patch size / stride: 512 / 1536
- Patches per 5000×5000 tile: 3×3 = 9
- Expected train/validation patches: 1350 / 270
- Split unit: source tile. Patches from the same source tile are not divided across train and validation.

## How to run

1. Obtain the Inria Aerial Image Labeling Benchmark through its official source; this repository does not redistribute the dataset.
2. Make the dataset available in the Kaggle environment with the expected structure:
   `AerialImageDataset/train/images/*.tif` and `AerialImageDataset/train/gt/*.tif`.
3. Run `tile_patch_mapping_generator.py` in a Python/Kaggle environment with OpenCV, NumPy, and PyTorch installed.
4. Check the generated `inria_tile_split.txt` and verify that the tile and patch counts match `tile_split_master.txt`.

The script may download the ImageNet-pretrained ResNet18 weights if they are not already mounted. Network access is therefore needed unless the weights are supplied locally.

## Important scope and reproducibility note

These files document the split protocol and deterministic patch preparation. They do **not**, by themselves, provide the Step 2/Step 3 model-training code, trained checkpoints, complete training logs, or proof that the metrics in `Inria_final_metrics.csv` were produced from this exact split. Those artifacts should be added separately if available, and the metrics should only be described as generated by this protocol after their provenance is confirmed.

The Inria results are intended as single-seed, sparsely sampled, tile-level supplementary mechanism validation—not as a benchmark or a claim of cross-domain generalization.

## Data and model assets

The original Inria imagery and labels are not redistributed. Model checkpoints are not included in this folder.
